## 1. Executive Summary

Today `copilot-bootstrap` only runs inside GitHub Copilot Chat. Users on Claude Desktop, Cursor, Continue, Zed, or custom LangChain apps cannot use its skills. Meanwhile, the Model Context Protocol (MCP) has become the de-facto cross-IDE standard for exposing tools and resources to any LLM host. This spec wraps the most valuable bootstrap capabilities as an **MCP server** so the harness is portable across every MCP-compatible client.

The server exposes a curated subset — not every skill — chosen by two criteria: (a) high reuse value outside Copilot, (b) safe-to-expose (no destructive side-effects without explicit consent). Capabilities fall into three buckets: **analyze** (read-only), **generate** (produces artifacts as text), **audit** (runs checks, returns diagnostics).

### Architecture snapshot

```
Today:                               After this spec:
  Copilot Chat ──▶ .github/ skills     Any MCP client
                                         │
                                         ▼
                                       bootstrap-mcp (stdio or http)
                                         │
                                         ├─ tools/
                                         │   analyze_repo, generate_spec,
                                         │   audit_context, detect_drift, ...
                                         │
                                         ├─ resources/

                                         │   .github/domains/, specs/*/spec.md
                                         │
                                         └─ prompts/
                                             bootstrap-copilot, specify-feature, ...
```

## 2. Problem Statement

### Current State

| Gap | Symptom | Impact |
|---|---|---|
| IDE lock-in | Only works in Copilot Chat | Claude Code / Cursor / Zed users excluded |
| Skills reinvented per client | Anyone wanting our logic in their app rewrites it | Fragmentation |
| No machine boundary | Skills are markdown read by the LLM; no deterministic API | Hard to unit-test; hard to automate |
| Cross-agent orchestration impossible | Another agent framework can't call our skills | No reuse in LangChain / AutoGen / etc. |
| Enterprise adoption friction | Enterprise Copilot-CLI-compatible endpoints exist, but local dev on Cursor is common; asymmetric experience | Slower internal rollout |

### Desired State

1. An MCP server implementation that **embeds** the bootstrap skill logic and exposes it as MCP tools, resources, and prompts.
2. Tools are strongly-typed (JSON schema inputs/outputs); no "read the markdown and hope".
3. Server runs locally over stdio (default) for dev and HTTP+bearer for shared team use.
4. Read vs write tools are clearly separated; write tools require explicit client consent surfaced via `elicit`/capability negotiation.
5. No runtime Copilot dependency: server works even if Copilot Chat is uninstalled.
6. Ships as a standalone package (`bootstrap-mcp`) so it can be installed in Claude Desktop / Cursor with a one-line config.
7. Telemetry piggybacks the spec-008 JSONL trace format for cross-surface observability.

### Business Impact (targets)

| Metric | Current | Target | How measured |
|---|---|---|---|
| MCP-capable clients supported | 0 | ≥ 3 (Claude Desktop, Cursor, Continue, Zed) | Manual verification matrix |
| Tools exposed | 0 | ≥ 8 read, ≥ 4 generate, ≥ 3 audit | Server `tools/list` response |
| Time to "first usable result" in a fresh client | — | < 5 min from install to first tool call | Docs quickstart timing |
| Skills reused as library from non-Copilot code | 0 | ≥ 5 | Adoption survey |
| Parity with in-Copilot behavior | — | All exposed tools produce identical artifacts to their in-Copilot equivalents | Bench compare (spec 010) |

## 4. User Stories

### US-1: Server skeleton + stdio transport

**As a** Cursor developer,
**I want** to launch `bootstrap-mcp` via stdio and see it registered,
**So that** I can call its tools from Cursor's MCP config.

**Acceptance Criteria:**
- [ ] AC-1: Given I install the package, When I configure my client with `"command": "bootstrap-mcp", "args": ["--stdio"]`, Then the server starts and responds to MCP `initialize` with protocol version + declared capabilities (tools, resources, prompts).
- [ ] AC-2: Given the server starts, When I call `tools/list`, Then I get a JSON array of registered tools each with `name`, `description`, `inputSchema` (JSON Schema draft-7+), and `annotations.destructive` flag.
- [ ] AC-3: Given the server runs, When it is asked for server info, Then it returns: name `bootstrap-mcp`, version matching `.github/VERSION`, homepage URL, trace file path if enabled.
- [ ] AC-4: Given an invalid request, When it arrives, Then the server responds with structured MCP error codes (not a crash) and logs a redacted line.
- [ ] AC-5 (**Security**): Given stdio is the default, When HTTP transport is enabled, Then it requires a bearer token from an env var and refuses to start on `0.0.0.0` without an explicit `--allow-public` flag.

**Priority:** Must Have

### US-2: Read-only analysis tools

**As a** LangChain builder,
**I want** to call `analyze_repo` and `detect_drift` programmatically,
**So that** my custom agent can understand a codebase using bootstrap's logic.

**Acceptance Criteria:**
- [ ] AC-1: Given tool `analyze_repo(path: string)`, When called on a valid repo, Then it returns JSON conforming to `analysis.schema.json` with detected stacks, modules, domain hints, and risk notes — same output shape as the `analyze-codebase` skill produces inside Copilot.
- [ ] AC-2: Given tool `detect_drift(path: string)`, When called, Then it returns JSON from the `drift-detector` skill logic.
- [ ] AC-3: Given tool `audit_context(agent: string, filepath: string)`, When called, Then it returns the simulated loaded context list + total KB + budget flags from `context-assembly-simulator`.
- [ ] AC-4: Given tool `audit_tools(path: string)`, When called, Then it returns the agent × tool matrix from `tool-permission-auditor`.
- [ ] AC-5: Given tool `list_skills(path: string)`, When called, Then it enumerates skills with description, triggers, and an `invocable_via_mcp` boolean.
- [ ] AC-6: Given read-only tools, When called, Then they never write files nor execute user shell commands (enforced by a capability wrapper).
- [ ] AC-7: Given a tool fails, When error surfaces, Then the error message is actionable (what was expected vs found) and redacted of secrets.

**Priority:** Must Have

### US-3: Generate tools (artifact producers)

**As a** Claude Desktop user,
**I want** to generate a spec or PR description for my current project,
**So that** I use bootstrap authoring skills without Copilot.

**Acceptance Criteria:**
- [ ] AC-1: Given tool `generate_spec(description: string, target_path: string)`, When called, Then it returns the `spec.md` content as text AND, if `write: true` in input, writes to `target_path` only after a `resources/list_changes` preview step.
- [ ] AC-2: Given tool `generate_pr_description(base: string, head: string)`, When called on a local repo, Then it returns the markdown body (never pushes anywhere).
- [ ] AC-3: Given tool `generate_hooks(stack: string)`, When called, Then it returns the hook JSON(s) as an array of `{path, content}` — host decides whether to write them.
- [ ] AC-4: Given tool `generate_tasks(spec_path: string)`, When called, Then it returns the tasks.md content using `generate-tasks` skill logic.
- [ ] AC-5: Given any generate tool, When called, Then the output carries a `provenance: {tool, version, inputs_hash}` block so consumers can audit origin.
- [ ] AC-6 (**Consent**): Given a generate tool can write files, When `write: true`, Then the server either (a) emits an MCP `elicit` consent request OR (b) refuses unless a per-session consent flag was set at init; never silently writes.

**Priority:** Must Have

### US-4: Audit tools (diagnostic)

**As a** Tech Lead,
**I want** to run discoverability/context/tool-permission audits from outside Copilot,
**So that** my platform team can include them in internal CI.

**Acceptance Criteria:**
- [ ] AC-1: Given tool `audit_discoverability(path)`, When called, Then it returns the `skill-discoverability-audit` scored report as JSON.
- [ ] AC-2: Given tool `validate_bootstrap_output(path)`, When called, Then it returns the quality verdict + list of stale/generic files.
- [ ] AC-3: Given audits produce text reports, When returned over MCP, Then both `markdown` and `json` representations are included so UIs can render nicely.
- [ ] AC-4: Given an audit tool finds a Constitution violation, When it reports, Then each finding has `article_id`, severity, and suggested remediation text.

**Priority:** Should Have

### US-5: Resources (bundle files as MCP resources)

**As a** Cursor developer,
**I want** bootstrap's canonical docs (constitution, source-of-truth map, domains) to be auto-attached,
**So that** the model in my client reasons with the same ground truth.

**Acceptance Criteria:**
- [ ] AC-1: Given the server runs against a repo path, When I list resources, Then it returns at minimum: `constitution.md`, `SOURCE-OF-TRUTH.md` (if present), `MODULE-ARCHITECTURE.md` (if present), each `.github/domains/*.md`, and each `specs/*/spec.md`.
- [ ] AC-2: Given a resource is fetched, When returned, Then content is trimmed to a token budget configurable per client; oversized resources return a summary plus a cursor for full retrieval.
- [ ] AC-3: Given the host supports subscriptions, When a resource file changes on disk, Then the server emits `notifications/resources/updated`.
- [ ] AC-4: Given resources may contain secrets (unlikely but possible), When served, Then `redact-sensitive-data` runs in-flight.

**Priority:** Should Have

### US-6: Prompts (slash-prompt portability)

**As a** Claude Desktop user,
**I want** `/bootstrap-copilot`, `/speckit-specify`, `/autorun` equivalents available as MCP prompts,
**So that** muscle memory from Copilot works in other clients.

**Acceptance Criteria:**
- [ ] AC-1: Given I list prompts, When called, Then it returns at minimum: `bootstrap-copilot`, `specify-feature`, `plan-implementation`, `generate-tasks`, `implement-feature`, `review-code-changes`, each with an `arguments` schema.
- [ ] AC-2: Given I call a prompt with arguments, When invoked, Then the server returns a rendered message list the host can send to its LLM.
- [ ] AC-3: Given a prompt references a tool, When rendered, Then the rendered message includes MCP tool-use instructions pointing to the server's own tools (works across hosts that support tool-use).

**Priority:** Could Have

### US-7: HTTP + auth transport for team deployments

**As a** Platform Engineer,
**I want** to run a shared `bootstrap-mcp` on an internal host with SSO/bearer auth,
**So that** my team uses a single blessed version.

**Acceptance Criteria:**
- [ ] AC-1: Given `bootstrap-mcp --http --port 7823 --auth-env BOOTSTRAP_MCP_TOKEN`, When it starts, Then it requires `Authorization: Bearer <token>` on every request.
- [ ] AC-2: Given an unauthorized request, When received, Then the server responds `401` with an MCP-compliant error body and logs the redacted source IP.
- [ ] AC-3: Given HTTP mode, When a write/generate tool with `write: true` is called, Then the server requires a per-session consent token issued at `initialize` with signed audit log entry.
- [ ] AC-4: Given shared deployments, When a request arrives, Then tool invocations append to an audit log (`.bootstrap-mcp/audit.log`) with user, tool, inputs hash, outcome.
- [ ] AC-5 (**Negative**): Given HTTP binding to `0.0.0.0`, When `--allow-public` is not set, Then startup fails with a clear error.
- [ ] AC-6 (**DoS**): Given a client spams requests, When rate > configured QPS, Then the server responds `429` and sheds excess load.

**Priority:** Could Have

### US-8: Install & config DX

**As a** new user,
**I want** to install and register `bootstrap-mcp` in Claude Desktop or Cursor in one step,
**So that** I can try it in under 5 minutes.

**Acceptance Criteria:**
- [ ] AC-1: Given `pipx install bootstrap-mcp` OR `npm i -g bootstrap-mcp` (depending on chosen runtime — see open questions), When run, Then the binary is on PATH.
- [ ] AC-2: Given `bootstrap-mcp init --client claude-desktop`, When run, Then it prints the exact JSON block to add to the client's MCP config and optionally patches it with `--write`.
- [ ] AC-3: Given the README quickstart is followed, When a fresh user times it, Then they reach a first successful `analyze_repo` response in under 5 minutes.
- [ ] AC-4: Given a supported client list (Claude Desktop, Cursor, Continue, Zed, VS Code), When `init --client <name>`, Then the correct per-client path is used.

**Priority:** Should Have

## 6. Non-Functional Requirements

| ID | Requirement | Target |
|---|---|---|
| NFR-1 | Startup time | < 1.5 s cold stdio init |
| NFR-2 | Tool call P95 latency for read tools on a typical repo | < 2 s |
| NFR-3 | Memory footprint | < 250 MB resident |
| NFR-4 | Security | No outbound network in default mode; HTTP transport opt-in; writes require consent |
| NFR-5 | Logging | All logs redacted via `redact-sensitive-data` before emission |
| NFR-6 | Packaging | Single-binary install via one language runtime (see open question) |
| NFR-7 | Parity | Generate-tools produce byte-identical artifacts to the in-Copilot skill equivalent given identical inputs (tested by spec-010 bench) |
| NFR-8 | Backward compat | Tool input schemas follow semver; breaking changes bump major |

## 7. Scope

### In scope

- MCP server exposing curated subset: ≥ 8 read, ≥ 4 generate, ≥ 3 audit tools
- Stdio + HTTP transports with auth on HTTP
- Resources for bundle truth files
- Prompts for canonical slash prompts
- `init` helper for client config
- Spec-008 trace compatibility
- Quickstart docs + per-client install recipes

### Out of scope

- Full 1:1 re-implementation of every skill (curate, don't mirror)
- Hosted SaaS deployment (mentioned as C3 moonshot separately)
- Windows service / systemd unit files (provide docs, not install scripts)
- Model inference inside the server (the server does *not* call an LLM — the host client does; server only provides tools/resources/prompts)

## 8. Assumptions

- A1: Skill logic can be extracted into pure functions or invoked via a sub-process harness so the MCP server is not dependent on a specific LLM.
- A2: Target clients (Claude Desktop, Cursor, Continue, Zed, VS Code) support the MCP protocol version we target.
- A3: The repo path is provided explicitly by the client; server does not auto-discover cross-repo.
- A4: Generate tools return content; the host client decides whether/where to write unless `write: true` + consent granted.

## 9. Open Questions

- **[NEEDS CLARIFICATION: runtime language]** — Python (matches existing skill ecosystem, spec-kit) vs TypeScript (matches vscode-copilot-chat) vs Rust (fastest, smallest binary)?
- **[NEEDS CLARIFICATION: how skill logic is invoked]** — (a) port each skill to a pure function in the server runtime, (b) shell out to a Copilot-compatible CLI, (c) spawn a headless agent per call? Each has drastically different cost and parity profiles.
- **[NEEDS CLARIFICATION: curated tool list]** — which 8+4+3 tools ship in v1? Suggestion in plan.md.
- **[NEEDS CLARIFICATION: telemetry opt-in/out]** — trace file on by default?
- **[NEEDS CLARIFICATION: MCP protocol version floor]** — oldest version we support; affects `elicit` availability.
- **[NEEDS CLARIFICATION: auth format for HTTP]** — bearer only, or also mTLS / OAuth?
- **[NEEDS CLARIFICATION: write-tool default posture]** — refuse by default vs prompt by default?
- **[NEEDS CLARIFICATION: licensing]** — MIT for the server binary? Same as bundle or split?

## 10. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Output drift between server and in-Copilot skill | High | Trust erosion | Parity test in spec-010 bench; release-gate on drift |
| Security: arbitrary host serves generate tool with write=true | Medium | Silent repo mutation | Consent required; session flag; audit log |
| Maintenance burden of multi-transport + multi-client | Medium | Slow iteration | Start stdio-only; HTTP behind a flag |
| Runtime choice lock-in | Medium | Ecosystem friction | Decide early; document reversal cost |
| Skill → pure-function extraction is harder than expected | High | Schedule slip | Pilot with 2 skills (analyze_repo + audit_context) before committing to full scope |
| MCP protocol churn | Medium | Compatibility breaks | Pin SDK; track LTS protocol version; release often |
| Prompt/resource content leaks repo secrets | Medium | High | In-flight redaction gate + unit tests on adversarial inputs |
