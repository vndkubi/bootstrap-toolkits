## 1. Executive Summary

Right now there is no objective way to answer *"Is today's `copilot-bootstrap` better than last week's?"* We ship changes to skills, agents, instructions, and hooks based on intuition and code-review feel. Meanwhile the ML community has moved to **eval-driven development**: every PR runs a standard benchmark and pass-rate/cost deltas gate the merge. This spec brings the same discipline to harness engineering.

We introduce a **Harness Benchmark Suite**: a small, versioned set of reference repos + standardised tasks ("golden PBIs") that `/autorun` can be evaluated against. Each bench run produces a scorecard (pass-rate, tokens, wall-time, review round-trips). Scorecards are committed, diffed across versions, and optionally gated in CI. Unlike SWE-bench (evaluates models), this evaluates **harness config quality** while holding the model fixed.

### Architecture snapshot

```
PR opens:                                 Result:
  tests/harness-bench/run.py               → scorecard-<git-sha>.json committed to
     ├─ fixtures/                             .github/.benchmarks/
     │    ├─ repo-java-enterprise/         → regression-report.md as PR comment
     │    ├─ repo-python-fastapi/          → CI gate: fail if pass-rate drops >5 pp
     │    ├─ repo-dotnet-ef/                  or tokens rise >15%
     │    └─ repo-mobile-android/          → dashboard.md updated weekly
     │
     └─ golden-pbis/
          ├─ 001-add-list-endpoint.md
          ├─ 002-fix-n-plus-one.md
          └─ ...
```

## 2. Problem Statement

### Current State

| Gap | Symptom | Impact |
|---|---|---|
| No objective quality signal | "Does this PR improve bootstrap?" answered by review feel | Regressions ship silently |
| No cost tracking | Token spend per skill unknown | Expensive skills stay expensive |
| No regression catching | New skill breaks old flow; no one notices until a user reports | Trust decays |
| No cross-stack coverage | Changes tested only on dev's local repo | Stack-specific breakage |
| Pre-bootstrap validation is structural only | `validate-bootstrap-output` checks file shape, not task success | Well-formed but useless configs pass |
| No shared baseline | Different contributors benchmark different things | Can't compare work |

### Desired State

1. A `tests/harness-bench/` folder with 4–6 reference repos and 15–25 golden PBIs.
2. A single entry point `npm run bench` (or stack-appropriate) runs the full suite in < 30 min locally and < 15 min in CI.
3. Every bench run produces a versioned scorecard committed under `.github/.benchmarks/`.
4. PR CI comments a scorecard diff vs `main`; merge is blocked if the delta violates configured gates.
5. A weekly cron run refreshes the dashboard at `.github/.benchmarks/dashboard.md`.
6. Bench can run under VS Code agent mode (dev loop) and Copilot CLI headless (CI) identically.
7. Token/cost accounting is honest: runs that hit cache are flagged; cold runs are used for official numbers.

### Business Impact (targets)

| Metric | Current | Target | How measured |
|---|---|---|---|
| % of bootstrap-config PRs with bench scorecard | 0 | 100 | CI artifact presence |
| Undetected regressions reaching main | Unknown (assume ≥ 2/quarter) | 0 per quarter | Post-merge revert count |
| Time to detect a config regression | Days–weeks | < 1 hour (on PR) | CI run time |
| Stack-specific pass-rate variance | Untracked | Reported per stack in scorecard | Scorecard field |
| Avg tokens per golden-PBI completion | Untracked | −20% YoY target | Scorecard trend |

## 4. User Stories

### US-1: Benchmark fixtures

**As a** Toolkit Maintainer,
**I want** a versioned set of reference repos that represent our target stacks,
**So that** every bench run exercises the same ground truth.

**Acceptance Criteria:**
- [ ] AC-1: Given `tests/harness-bench/fixtures/`, When I inspect it, Then it contains ≥ 4 reference repos covering at least: Java/Maven, .NET/EF Core, Python/FastAPI, TS/React. Mobile is a stretch goal.
- [ ] AC-2: Given a reference repo, When bench runs, Then it is checked out into an ephemeral worktree (no mutation of fixtures); fixtures are pinned by commit sha.
- [ ] AC-3: Given fixture repos may contain secrets in reality, When shipping, Then fixtures are **minimal synthetic projects** authored for bench; no production code imported.
- [ ] AC-4: Given a fixture is updated, When the change lands, Then its commit sha is bumped in `tests/harness-bench/fixtures.lock.json` and existing scorecards are marked `stale`.
- [ ] AC-5 (**Security**): Given fixtures are user-controlled inputs to the harness, When bench processes them, Then shell execution inside fixtures is denied by default (sandboxed via existing hook permission mechanism).

**Priority:** Must Have

### US-2: Golden PBI catalog

**As a** Toolkit Maintainer,
**I want** a catalog of standardised tasks (golden PBIs) with expected outcomes,
**So that** task success is unambiguously measurable.

**Acceptance Criteria:**
- [ ] AC-1: Given `tests/harness-bench/golden-pbis/`, When I inspect it, Then each PBI is a markdown file with: id, intent, target fixture, acceptance checks (machine-evaluable), expected artifact paths, difficulty label.
- [ ] AC-2: Given a PBI runs, When the loop finishes, Then a scorer computes pass/fail by running the PBI's acceptance checks (shell commands against the fixture: tests pass, endpoint reachable, schema valid, etc.).
- [ ] AC-3: Given a PBI has a `negative` expected outcome (e.g., "harness should refuse because spec is too vague"), When the loop correctly refuses/pauses, Then it counts as a pass.
- [ ] AC-4: Given the catalog covers at least: CRUD endpoint addition, bug-fix from stack trace, test generation, code review, security-finding triage, documentation generation, refactor-within-module, spec-authoring for ambiguous input, cross-module impact change. Min 15, target 25.
- [ ] AC-5: Given an AC check is flaky (determinism failure > 5% over 20 runs), When detected, Then the PBI is auto-quarantined with a tracking issue.

**Priority:** Must Have

### US-3: Scorecard output

**As a** Contributor,
**I want** a machine-readable + human-readable scorecard per bench run,
**So that** I can compare my PR against baseline.

**Acceptance Criteria:**
- [ ] AC-1: Given bench finishes, When scorecard is written, Then a JSON file at `.github/.benchmarks/<git-sha>/scorecard.json` conforms to `scorecard.schema.json` containing: pass-rate overall + per-stack + per-difficulty, total tokens, wall-time, round-trips-per-PBI, harness version.
- [ ] AC-2: Given the same git sha, When bench re-runs, Then the scorecard is versioned by run id (not overwritten), and a `latest.json` symlink/pointer tracks the newest.
- [ ] AC-3: Given a human-readable markdown at `.github/.benchmarks/<git-sha>/report.md`, When rendered, Then it shows pass/fail per PBI with 1-line reason for failures and top-3 token hot-spots.
- [ ] AC-4: Given a run produces secrets or tokens in logs, When the scorecard is written, Then `redact-sensitive-data` runs first.

**Priority:** Must Have

### US-4: PR CI gate

**As a** Toolkit Maintainer,
**I want** CI to comment a scorecard diff on every PR and block regressions,
**So that** bad changes don't reach main.

**Acceptance Criteria:**
- [ ] AC-1: Given a PR touches `.github/` or `tests/harness-bench/`, When CI runs, Then it executes the bench subset appropriate to the changed files (see change-detection table in plan.md) and posts a comment with the delta table.
- [ ] AC-2: Given the delta shows pass-rate drop > 5 pp OR token rise > 15% (thresholds configurable), When CI finishes, Then the job fails and merge is blocked.
- [ ] AC-3: Given the maintainer waives the gate (label `bench-override: <reason>`), When CI re-runs, Then the override + reason is recorded in the merged commit message.
- [ ] AC-4: Given a PR touches only docs unrelated to harness, When change-detection sees no relevant paths, Then the bench job is skipped (fast path).
- [ ] AC-5 (**Cost guard**): Given bench costs tokens, When a PR runs, Then it uses the configured capped budget; overrun halts the job with a clear message.

**Priority:** Must Have

### US-5: Weekly dashboard

**As a** Tech Lead,
**I want** a weekly trend view,
**So that** I can decide which bootstrap version to pin.

**Acceptance Criteria:**
- [ ] AC-1: Given a weekly cron, When it runs, Then it appends a row to `.github/.benchmarks/dashboard.md` with: date, git sha, overall pass-rate, per-stack pass-rate, median tokens, top failing PBI.
- [ ] AC-2: Given dashboard has > 20 rows, When rendered, Then older rows are moved to `.github/.benchmarks/archive/YYYY-MM.md` automatically.
- [ ] AC-3: Given pass-rate drops > 3 pp for 2 consecutive weeks, When the cron finishes, Then it opens a tracking issue (via configured GitHub adapter).

**Priority:** Should Have

### US-6: Model/harness matrix

**As a** Toolkit Maintainer,
**I want** to run the same bench against different model providers,
**So that** we know which harness improvements help which models.

**Acceptance Criteria:**
- [ ] AC-1: Given `bench.config.json` declares providers (e.g., `copilot-claude-sonnet-4.5`, `copilot-gpt-4.1`), When I run `bench --matrix`, Then scorecard is produced per provider.
- [ ] AC-2: Given a provider is unavailable (auth missing), When bench runs, Then that provider is skipped with a clear warning; job does not fail.
- [ ] AC-3: Given matrix runs produce a summary, When rendered, Then it tabulates pass-rate × model × stack.

**Priority:** Could Have

### US-7: Local dev loop

**As a** Contributor,
**I want** to run bench locally on just the PBIs affected by my change,
**So that** I iterate fast without full-suite cost.

**Acceptance Criteria:**
- [ ] AC-1: Given `bench --affected`, When I run it, Then only PBIs that touch changed files (per change-detection) run.
- [ ] AC-2: Given `bench --pbi <id>`, When I run it, Then only that single PBI runs.
- [ ] AC-3: Given a run, When I add `--no-network`, Then any outbound calls fail fast (supports offline / deterministic runs).

**Priority:** Should Have

## 7. Scope

### In scope

- 4–6 synthetic fixture repos (Java, .NET, Python, TS/React; Mobile stretch)
- 15–25 golden PBIs with machine-evaluable ACs
- Scorecard schema + runner + CI workflow + weekly dashboard
- Integration with `/autorun` as the driver (bench calls `/autorun <PBI> --harness=cli`)
- Affected-subset runner for local dev loop

### Out of scope

- Evaluating *model* quality (this bench fixes the model and measures harness)
- Fine-tuning / RLHF (explicitly deferred)
- Real customer repo bench (must be synthetic to be shareable)
- Visual UI dashboard (markdown is sufficient for v1; GUI later)

## 8. Assumptions

- A1: Spec 008 (`/autorun` with JSONL trace + CLI mode) is merged first. Bench fundamentally depends on a headless, trace-producing loop.
- A2: CI has network access to a Copilot-compatible model endpoint during the job (or a configured mock).
- A3: Fixtures remain small (< 10 MB each); they are checked in or referenced via git submodule.
- A4: Token cost accounting is read from the harness trace, not the model vendor billing API (vendor billing is informational only).

## 10. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Bench becomes flaky → team loses trust | High | Bench ignored | Auto-quarantine flaky PBIs; explicit determinism NFR |
| Cost runaway in CI | Medium | Budget overrun | Per-run token cap; matrix off by default |
| Fixtures diverge from real-world repos | High | Bench looks green but real repos fail | Refresh fixtures quarterly; supplement with occasional real-repo spot checks |
| Over-fitting harness to bench | Medium | Local success, real regression | Rotate a holdout PBI set each release |
| Maintenance burden of 25 PBIs | High | Suite rots | Quarterly review; archive unused PBIs |
| CI secrets leak via scorecard | Low | High | Mandatory redaction gate; scorecards committed in plaintext |
