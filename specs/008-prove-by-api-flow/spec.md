## 1. Executive Summary

`copilot-bootstrap` currently produces a rich set of agents and skills, but a developer still has to manually stitch them together for every PBI: intake → investigate → plan → implement → test → review → PR. Each hand-off is chat-driven, and proof of correctness is unit tests with permissive mocking. This spec introduces an **autonomous, contract-first, evidence-driven loop** — `/autorun <PBI-id>` — that drives a PBI from requirement to a reviewable PR **without the developer choreographing every step**, and that **proves correctness by running API full-flow tests against real services with fixture data**, not by adding more mocks.

The loop runs entirely **local** (VS Code agent mode or Copilot CLI), produces a **machine-readable trace**, and attaches **objective evidence** (test report, API trace log, coverage, sequence diagram) to every PR. It hardens the existing `spec-kit` pipeline rather than replacing it.

> **Uncertainty Rule**: Any gap below is marked `[NEEDS CLARIFICATION: ...]` rather than assumed.

### Architecture: Before and After

```
BEFORE (today):                          AFTER (this spec):
PBI ──▶ developer manually:              /autorun PBI-123 ──▶ 7-phase loop:
  ask @business-analyst                    1. INTAKE      (spec.md)
  ask @investigator                        2. CONTRACT    (openapi.yaml, data-model)
  ask @dotnet-implementor                  3. TEST-FIRST  (failing API-flow tests)
  ask @test-specialist                     4. FIXTURE     (DB seed + WireMock)
  ask @code-reviewer                       5. IMPLEMENT   (TDD loop, red→green)
  ask @pr-manager                          6. REVIEW      (functional + technical)
                                           7. EVIDENCE    (PR body + artifacts)
Mocks everywhere, unit-test only.        Real services + fixtures, contract-tested.
PR = "trust me, tests pass".             PR = attached trace, report, diagram.
```

## 2. Problem Statement

### Current State

| Gap | Surface | Today | Impact |
|---|---|---|---|
| Manual orchestration | `@dev-orchestrator` | Routes one agent at a time, waits for chat turns | Slow, context lost between turns, inconsistent outputs |
| Implicit contract | spec → code | `plan-implementation` mentions contracts but does not enforce them | Implementation drifts from spec; tests can't be pre-generated |
| Test-after pattern | `@test-specialist` | Tests written after implementation, heavy on unit + mocks | Regressions at service boundaries; business flow not proven |
| Mock creep | reviews | "minimal mocks" is a guideline, not a gate | Reviewers accept mocks of internal services, hiding integration bugs |
| Opaque delivery | `@pr-manager` | PR body is prose | Reviewer must re-run tests to trust the claim |
| No feedback loop | `review-effectiveness` | Measures adoption, not correctness | Cannot detect when the generated config produces broken features |
| Harness drift | VS Code vs CLI | Prompts are authored for chat UI | Copilot CLI cannot run the same workflow unattended |

### Desired State

1. A single entry point `/autorun <PBI-id>` carries a PBI from intake to reviewable PR with minimum human interruption, stopping only at confirmation gates.
2. Every API-bearing feature produces `contracts/openapi.yaml` (or protocol equivalent) **before** any implementation code.
3. API full-flow tests are generated **from the contract**, committed **red**, and the implementation loop only completes when they go **green**.
4. Mocking is constitutionally restricted: only external 3rd-parties, paid APIs, non-determinism. Internal services are exercised for real using `testfixture`-seeded data.
5. Every PR attaches: test report, API trace log, coverage delta, sequence diagram (as-is vs to-be), and a Constitution gate checklist.
6. The loop runs identically under VS Code agent mode and Copilot CLI headless; traces are JSONL for later analysis.

## 4. User Stories

### Phase A — Autonomous Orchestration

#### US-A1: Single-entry `/autorun` command

**As a** Senior Dev,
**I want** a single prompt `/autorun <PBI-id>` that drives a PBI through 7 phases,
**So that** I stop choreographing agent hand-offs and only act at confirmation gates.

**Acceptance Criteria:**
- [ ] AC-1: Given a PBI reference, When I invoke `/autorun`, Then the loop resolves the reference using this **precedence**: (1) existing `specs/<id>-<slug>/` folder → reuse; (2) GitHub/Jira id pattern (`#NNN`, `PROJ-NNN`) → fetch body via configured adapter; (3) free text → generate slug + treat as description. Ambiguous inputs pause at a confirmation gate (no silent guessing).
- [ ] AC-2: Given resolution succeeds, When Phase 1 runs, Then the loop produces `specs/<id>-<slug>/spec.md` using `specify-feature`.
- [ ] AC-3: Given each phase completes, When the next phase starts, Then the loop emits a JSONL trace line `{schemaVersion, phase, agent, inputs, outputs, duration_ms, token_cost, gate?}` into `.github/.traces/autorun-<PBI>.jsonl`.
- [ ] AC-4: Given a phase produces a blocking question, When the loop detects it, Then it emits a **confirmation gate** conforming to the gate schema (see §8.1) and pauses; it does not invent business truth.
- [ ] AC-5: Given the user cancels, When `/autorun --abort` is invoked, Then the loop halts without leaving half-applied edits (git working tree clean or on a dedicated `autorun/<PBI>` branch); partial artifacts remain in the feature workspace clearly labelled `status: aborted`.
- [ ] AC-6: Given the loop reaches Phase 7 successfully, When it completes, Then a summary with artifact links is printed and a PR-ready commit/draft is produced.
- [ ] AC-7 (**Security**): Given untrusted PBI text, When the loop processes it, Then the text is passed only via structured context fields, never merged into system prompts; detected injection patterns (e.g., "ignore previous rules", "commit without tests") pause at a confirmation gate.
- [ ] AC-8 (**AuthZ**): Given Phase 5 needs shell/test execution, When the loop attempts it, Then it requests permission via the existing hook mechanism (`hookSpecificOutput.permissionDecision`); in CLI mode, an explicit `.github/autorun.allowlist` file must grant the repo + command classes or the loop halts.

**Priority:** Must Have

#### US-A2: Harness parity (VS Code + Copilot CLI)

**As a** Platform Engineer,
**I want** `/autorun` to work the same way under VS Code agent mode and Copilot CLI headless,
**So that** I can automate PBI execution in background runs without UI.

**Acceptance Criteria:**
- [ ] AC-1: Given `COPILOT_HARNESS=cli` or equivalent detection, When `/autorun` runs, Then it suppresses interactive previews and emits machine-readable status to stdout.
- [ ] AC-2: Given the harness is VS Code, When `/autorun` runs, Then it uses diff previews and inline markdown rendering.
- [ ] AC-3: Given either harness, When a confirmation gate is reached in CLI mode, Then the loop prints the question and exits with a non-zero status plus a resume token; re-invoking with `/autorun --resume <token>` continues from that gate.
- [ ] AC-4: Given a CI job runs `/autorun` on a sample repo, When the job finishes, Then the JSONL trace is valid, artifacts are present, and exit code reflects success or the specific gate reached.
- [ ] AC-5 (**Negative**): Given CLI runs with no TTY, Then confirmation gates emit machine-readable JSON on stdout and exit non-zero with a resume token; no interactive prompt is attempted.
- [ ] AC-6 (**Negative**): Given the harness lacks shell execution permission, Then Phase 5 halts at an AuthZ gate before any edit is applied.

**Priority:** Must Have

### Phase B — Contract-First Enforcement

#### US-B1: Mandatory contract artifact before implementation

**As a** Tech Lead,
**I want** Phase 2 to block until `contracts/openapi.yaml` (or stack equivalent) is committed and references all acceptance criteria,
**So that** implementation and tests are generated from a single source of truth.

**Acceptance Criteria:**
- [ ] AC-1: Given Phase 2 starts, When it classifies the feature, Then it assigns one of these **taxonomy** values: `api-rest`, `api-graphql`, `api-grpc`, `event-driven` (Kafka/SQS/queue), `library`, `cli`, `ui-only`, `mixed`. Classification uses spec content + `docs/02-architecture-map.md` when present; ambiguous cases pause at a confirmation gate (no keyword heuristic alone).
- [ ] AC-2: Given the taxonomy is `api-rest`/`api-graphql`/`api-grpc`/`event-driven`/`mixed`, When Phase 2 runs, Then it generates a `contracts/` folder with the appropriate artifact (OpenAPI / GraphQL SDL / protobuf / AsyncAPI) plus `data-model.md`.
- [ ] AC-3: Given the taxonomy is `library`/`cli`/`ui-only`, When Phase 2 runs, Then contract generation is skipped and the reason is recorded in the trace with the taxonomy value.
- [ ] AC-4: Given a contract is generated, When `@spec-reviewer` inspects it, Then every acceptance criterion is traceable to at least one operation/endpoint/event/message in the contract.
- [ ] AC-5: Given a contract exists and later spec.md changes, When `update-spec` runs, Then it re-emits or patches the contract and flags downstream tests as stale.

**Priority:** Must Have

#### US-B2: Quickstart script (real-local bootstrap)

**As a** Senior Dev,
**I want** a `quickstart.md` + script that starts the real local stack (devcontainer / docker-compose / `make dev` / native) and verifies health,
**So that** full-flow tests can hit real services without manual setup.

**Acceptance Criteria:**
- [ ] AC-1: Given a devcontainer is present, When Phase 2 emits quickstart, Then it reuses the devcontainer start command, not a new recipe.
- [ ] AC-2: Given `docker-compose.yml` is present, When Phase 2 emits quickstart, Then it reuses existing service names and ports.
- [ ] AC-3: Given neither exists and the stack is native (SpringBoot, .NET, Node), When Phase 2 emits quickstart, Then it produces the smallest working `run + healthcheck` recipe.
- [ ] AC-4: Given quickstart runs, When the healthcheck fails, Then the loop halts before Phase 5 (IMPLEMENT) with a diagnostic message.

**Priority:** Must Have

### Phase C — Test-First, Evidence-Over-Mocks

#### US-C1: API full-flow tests generated from contract (red first)

**As a** QA Engineer,
**I want** Phase 3 to generate API full-flow tests from the contract **before** any production code,
**So that** acceptance criteria become executable and the TDD loop has a concrete goal.

**Acceptance Criteria:**
- [ ] AC-1: Given a contract and acceptance criteria exist, When Phase 3 runs, Then it produces integration-level API tests hitting real endpoints (Given/When/Then blocks mapped 1-1 to ACs).
- [ ] AC-2: Given the tests are generated, When they run before implementation, Then they fail with clear "endpoint not implemented" or "assertion not yet satisfied" messages (not compile errors).
- [ ] AC-3: Given the stack is detected, When tests are generated, Then the right tooling is chosen based on repo evidence (RestAssured + JUnit5 / xUnit + WebApplicationFactory / supertest / pytest-httpx / XCTest URLSession / Espresso UI+API / AsyncAPI test harness for event-driven); defaults are never applied without repo evidence.
- [ ] AC-4: Given tests are committed, When viewed in the PR, Then coverage includes: happy path, ≥ 1 edge case per AC, ≥ 1 security/authorization case (if auth is in scope), and ≥ 1 injection/boundary case for endpoints that accept user input.
- [ ] AC-5: Given a non-API feature (`library`/`cli`/`ui-only`), When Phase 3 runs, Then it generates the nearest behavioural test (component test, CLI invocation test, UI interaction test) instead of being skipped.

**Priority:** Must Have

#### US-C2: Testfixture-seeded data, no internal mocks

**As a** QA Engineer,
**I want** Phase 4 to seed the real database with `testfixture` data and stub only external 3rd-party services,
**So that** tests exercise real business logic through real service boundaries.

**Acceptance Criteria:**
- [ ] AC-1: Given `@mock-data-specialist` runs in Phase 4, When it produces fixtures, Then each fixture is reusable (named builder/factory + SQL seed or equivalent) and referenced by at least one AC in the spec.
- [ ] AC-2: Given the feature needs an external paid/3rd-party service, When Phase 4 runs, Then it generates a WireMock (or stack equivalent) stub with success, error, and timeout scenarios — not inline mocks in tests. Stubs MUST use **synthetic data only**; captured real responses are rejected by a PII scan gate.
- [ ] AC-3: Given an internal service is reachable via the local stack, When tests are generated, Then that service is called for real; mocking an internal service is flagged as an **Article X violation** and requires a co-signed ADR at `.artifacts/<PBI>/mock-exceptions.md` to proceed.
- [ ] AC-4: Given tests use a shared DB, When they run, Then each test isolates via transaction rollback, schema reset, or dedicated fixture keys (no flaky cross-test pollution).
- [ ] AC-5 (**Secrets**): Given the real stack needs credentials, When fixtures or stubs reference them, Then only synthetic/dev values are used; production-shaped secrets are rejected at commit time by a pre-commit scanner.

**Priority:** Must Have

#### US-C3: TDD implement loop (red → green → refactor)

**As a** Senior Dev,
**I want** Phase 5 to loop "run tests → read failure → patch → run again" until green or a budget is exhausted,
**So that** I don't watch the agent spin; I get a result or a concrete blocker.

**Acceptance Criteria:**
- [ ] AC-1: Given failing tests exist, When Phase 5 starts, Then it runs the test command, parses failures, edits code, and re-runs — up to `tddLoop.maxIterations` (see §8.2 config surface; default 8).
- [ ] AC-2: Given the loop makes no progress for `tddLoop.noProgressThreshold` consecutive iterations (default 2, same failing tests), When detected, Then it halts, emits a diagnostic, and returns to the user with the failing test signatures.
- [ ] AC-3: Given the loop reaches all-green, When finishing, Then it runs a **scoped regression**: the changed-module test suite plus any cross-module tests listed in the `impact-analysis` skill output. Scope is recorded in the trace. Running the entire repo suite is opt-in via `tddLoop.regression=full`.
- [ ] AC-4: Given the loop exceeds the iteration budget, When halting, Then no tests are disabled or deleted to force green (this is a Constitution violation flagged by `@functional-reviewer`).
- [ ] AC-5: Given each iteration runs, When it completes, Then a trace line is emitted with iteration number, failing count, diff summary, and duration.

**Priority:** Must Have

### Phase D — Review, Evidence, and Learning

#### US-D1: Two-stage review with evidence inputs

**As a** Tech Lead,
**I want** Phase 6 to run functional review → technical review using the existing `review-code-changes` pipeline, but fed with the evidence bundle,
**So that** review catches business errors before style errors.

**Acceptance Criteria:**
- [ ] AC-1: Given Phase 5 produced green tests, When Phase 6 starts, Then `@functional-reviewer` runs first against spec + AC + test results; if business logic is wrong, it rejects without escalating.
- [ ] AC-2: Given functional review passes, When `@technical-reviewer` runs, Then it receives the evidence bundle paths explicitly and may reference them in findings.
- [ ] AC-3: Given the reviewer flags an internal-service mock, When detected, Then it is a Blocker (Article X, plan.md) — no override without an ADR.
- [ ] AC-4: Given review finishes, When producing the verdict, Then it emits both human summary and a JSON finding list consumable by `review-memory-promotion`.

**Priority:** Must Have

#### US-D2: Evidence bundle attached to PR

**As a** Tech Lead,
**I want** every PR from `/autorun` to carry an evidence bundle so I review claims, not prose,
**So that** I can approve in minutes, not by re-running everything locally.

**Acceptance Criteria:**
- [ ] AC-1: Given Phase 7 runs, When `@pr-manager` composes the PR body, Then it includes the Constitution gate checklist with each gate marked ✅ / ⚠️ / ❌ with links.
- [ ] AC-2: Given artifacts exist, When the PR is created, Then a committed `evidence-summary.md` in the feature workspace links to (not embeds) `.artifacts/<PBI>/api-trace.log`, test report, coverage, and `sequence.md`. Full bundle stays local by default (`.gitignore`d) or uploads to CI artifact storage when configured.
- [ ] AC-3: Given mocks were used, When the PR body is written, Then a "Mocks used" section lists each with category (external / non-determinism / paid API) — internal mocks are absent or the PR is blocked per Article X.
- [ ] AC-4: Given the PR is created as draft, When the `/autorun` command exits, Then the draft URL (or local diff location in CLI mode) is printed.
- [ ] AC-5 (**Secrets**): Given the evidence bundle is assembled, When it is written, Then a redaction filter strips `Authorization`/`Cookie` headers, env vars matching `*_KEY|*_TOKEN|*_SECRET|*_PASSWORD`, and JWT payload claims; a secrets-scan gate blocks commit if any slip through.

**Priority:** Must Have

#### US-D3: Trace feeds learning loop

**As a** Toolkit Maintainer,
**I want** every `/autorun` run to feed its trace into `review-effectiveness` and `correction-ledger`,
**So that** we learn which phases stall, which gates fire too often, which agents redirect users.

**Acceptance Criteria:**
- [ ] AC-1: Given a run completes, When `.github/.traces/autorun-<PBI>.jsonl` exists, Then `review-effectiveness` can aggregate runs across time to report per-phase success rate and average duration.
- [ ] AC-2: Given the user redirects or corrects an agent during the loop, When detected, Then the event is tagged and consumed by `correction-ledger` via existing capture hook.
- [ ] AC-3: Given patterns emerge (e.g. Phase 2 fails for Python repos), When `repo-memory-promoter` runs, Then those patterns surface as promotion candidates.

**Priority:** Should Have

## 7. System Context

### Architecture Overview

`/autorun` sits **above** the existing spec-kit skills and agents; it is a deterministic state machine whose states map to existing skills. It does **not** replace them. The only brand-new artifacts are: 1 prompt, 1 agent, 4 skills, 1 hook, 1 constitution article, 1 PR template section, 1 trace schema.

### External Dependencies

| System | Integration | Purpose | Owner |
|---|---|---|---|
| Copilot CLI | Entry harness | Headless execution | Platform |
| VS Code Copilot | Entry harness | Interactive execution | Platform |
| Git | Repo state | Apply edits, create branch, push draft PR | Dev |
| Docker / devcontainer | Local stack | Real services for Phase 4-5 | Dev |
| WireMock (or stack equivalent) | External stub | Only for 3rd-party services | Dev |

### Data Flow (high level)

PBI-id → INTAKE (`spec.md`) → CONTRACT (`contracts/`, `data-model.md`, `quickstart.md`) → TEST-FIRST (`tests/...` red) → FIXTURE (`fixtures/`, `wiremock/`) → IMPLEMENT (src/… + tests green) → REVIEW (findings) → EVIDENCE (PR body + `.artifacts/`). A detailed sequence diagram will be produced during planning.

## 8. UI/UX Requirements

Interactive surface is chat / CLI text, not GUI. Key UX rules:

- Every phase starts with a one-line banner: `── Phase N/7 — NAME ──`.
- CLI mode prints `▶ RESUME TOKEN: <token>` when pausing and exits non-zero.
- VS Code mode renders the evidence bundle links as clickable markdown.

### 8.1 Confirmation-gate schema (single source of truth)

All 7 phases emit gates conforming to this schema:

```json
{
  "schemaVersion": "1",
  "phase": 1-7,
  "gateId": "string (stable, kebab-case)",
  "question": "one sentence",
  "options": ["optional enumerated answers"],
  "default": "option or null",
  "blocking": true,
  "resumeToken": "opaque string",
  "category": "business | authz | security | taxonomy | config"
}
```

- VS Code renders `options` as buttons + free-text box.
- CLI emits the JSON on stdout and exits with code `10 + phase` (e.g. Phase 2 gate → exit 12).
- `category=authz` and `category=security` gates are **never** auto-answered by defaults.

### 8.2 Config surface

A single file `.github/autorun.config.json` governs tunables; unknown keys error loudly.

| Key | Default | Purpose |
|---|---|---|
| `tddLoop.maxIterations` | 8 | Hard cap on red→green iterations |
| `tddLoop.noProgressThreshold` | 2 | Consecutive identical-failure iterations before halt |
| `tddLoop.regression` | `scoped` | `scoped` or `full` |
| `cost.tokenCap` | 200000 | Soft cap; exceeding triggers a gate |
| `artifacts.mode` | `local-gitignored` | `local-gitignored`, `ci-upload`, or `lfs` |
| `pbi.resolver.order` | `["folder", "github", "jira", "freetext"]` | Precedence for `/autorun <ref>` resolution |
| `taxonomy.autoClassify` | `true` | If false, always pauses at a taxonomy gate |

### Reversibility

- Every `/autorun` creates a dedicated branch `autorun/<PBI>`; all edits land there, never on `main`.
- `--abort` resets the working tree to the branch base and removes uncommitted artifacts; the branch remains for inspection.
- `--revert <PBI>` deletes the branch and marks `specs/<id>-<slug>/spec.md` with `status: reverted` + a changelog entry.
- PR drafts stay in draft state until a human merges; Article X blockers require the draft to be closed or the exception ADR to be committed.

### Article X Governance (resolved)

- **Location**: Article X "Evidence over Mocks" is added to `.github/constitution.md` as a Phase -1 + review gate with a changelog entry `chore(constitution): add Article X`.
- **Scope**: Prohibits mocking internal services (own modules, own DB, own repositories). Allows mocks only for external 3rd-party, paid APIs, non-determinism (clock/random/UUID).
- **Exception path**: An internal mock is permitted only if `.artifacts/<PBI>/mock-exceptions.md` exists with (a) rationale, (b) rollback plan, (c) co-signatures from the feature owner **and** a tech lead distinct from the feature owner. `@functional-reviewer` reads this file and emits `articleX.compliant: true` only when signatures are present.
- **Enforcement**: Violations without an accepted exception ADR are Blockers; `@pr-manager` refuses to mark the PR ready-for-review.

### Assumptions
- Target repos expose runnable local stack (devcontainer, compose, or native) or the team accepts adding one. **Fallback**: if none of the three is detectable and the feature taxonomy is API-bearing, the loop halts at a Phase 2 gate suggesting `--skip-quickstart` (records an explicit assumption in the trace and downgrades evidence quality in the PR checklist). In-memory fallback is **not** allowed for API-bearing features.
- Copilot CLI supports custom prompt invocation with non-interactive flags. `[NEEDS CLARIFICATION: exact CLI invocation semantics + resume-token support — owner: Platform]`
- Post-edit hook can run shell commands safely in current hook runtime.
- Test frameworks per stack (RestAssured, xUnit, supertest, pytest, XCTest, Espresso, AsyncAPI test harness) are acceptable defaults; teams can override in instructions.
