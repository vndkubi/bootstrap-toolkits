## 1. Executive Summary

Today `copilot-bootstrap` learns from individual correction signals (accepted fixes, user redirections) but treats every new PBI as a cold start. When an agent implements the 5th "add pagination to list endpoint" task, it re-derives the same decisions from scratch — same research, same mistakes, same token cost. This spec introduces **Episodic Memory**: a structured record of completed tasks (successful *and* failed) that agents can **replay** as few-shot evidence when they encounter a similar task.

The feature builds on the JSONL trace already produced by `/autorun` (spec 008). Each completed episode is indexed by an embedding of its intent + key artifacts, scored by outcome quality, and surfaced to future runs via a new skill `trace-replay`. The goal, inspired by LangChain Deep Agents (Terminal-Bench 52.8% → 66.5% via harness changes alone), is to improve task success rate and reduce tokens **without changing the underlying model**.

### Architecture snapshot

```
Run N (today):                       Run N (this spec):
  /autorun PBI-X                       /autorun PBI-X
     │                                    │
     ▼                                    ▼
  cold reasoning                       trace-replay skill:
     │                                    │  1. embed(intent + contracts)
     ▼                                    │  2. top-k nearest episodes
  produce spec/plan/code                  │  3. filter by outcome_score ≥ threshold
     │                                    ▼
     ▼                                 inject 3 episodes as few-shot
  trace written then forgotten            │
                                          ▼
                                       produce spec/plan/code (warm start)
                                          │
                                          ▼
                                       trace written → indexed as episode
```

## 2. Problem Statement

### Current State

| Gap | Symptom | Impact |
|---|---|---|
| No episodic recall | Every PBI is cold-start, even for repeat patterns | Wasted tokens re-deriving decisions |
| Correction ledger is flat | Signals are atomic fixes, not end-to-end episodes | Cannot learn multi-step strategies |
| Traces are write-only | `/autorun` JSONL is read by humans in post-mortems only | Agents never benefit from their own history |
| Failure amnesia | When an approach failed last time, nothing prevents reattempt | Same bugs rediscovered |
| No quality signal on memory | Promoted memory treats every signal equally | Noise accumulates; precision decays |

### Desired State

1. Every `/autorun` completion writes a structured **episode** to `.github/.episodes/` (not just raw trace).
2. Each episode carries an **outcome score** derived from evidence (tests passed, review verdict, post-merge regressions).
3. A new skill `trace-replay` retrieves top-k relevant past episodes when a new task starts.
4. Agents receive episodes as **structured few-shot context**, not as raw chat transcripts.
5. Poor-outcome episodes are kept as **negative examples** ("don't do this — here's why").
6. Episode retrieval is measurable: A/B comparable against cold-start runs.

### Business Impact (targets)

| Metric | Baseline (spec 008) | Target | How measured |
|---|---|---|---|
| Tokens per completed PBI | Measured from first 20 `/autorun` runs with `--no-replay` after this ships (see Decision D-7) | −25% median | Trace `token_cost` sum |
| First-attempt test pass rate | Same 20-run baseline window (D-7) | +15 pp | Phase-5 (Implement) outcome |
| Repeat mistakes across similar PBIs | Unknown, ad-hoc | ≤ 1 per 10 similar episodes | Negative-episode hit rate |
| Episode index size on disk | 0 | < 50 MB for 500 episodes | File size check |
| Retrieval latency P95 | — | < 500 ms locally | `trace-replay` instrumentation |

## 4. User Stories

### US-1: Automatic episode capture

**As a** Toolkit Maintainer,
**I want** every completed `/autorun` run to be recorded as a structured episode,
**So that** future runs can learn from it without manual curation.

**Acceptance Criteria:**
- [ ] AC-1: Given `/autorun` reaches Phase 7 (Evidence) successfully, When it completes, Then a file `.github/.episodes/<YYYYMMDD>-<PBI-id>-<slug>.json` is written conforming to the Episode schema (see §8).
- [ ] AC-2: Given `/autorun` aborts or fails, When it terminates, Then a partial episode is still written with `outcome: aborted|failed` and the reason, so negative examples are preserved.
- [ ] AC-3: Given an episode is written, When it contains user-provided free text, Then that text is stored under a dedicated `raw_intent` field (never merged into summary text) so downstream replay cannot be prompt-injected.
- [ ] AC-4: Given secrets may appear in traces (tokens, keys), When the episode is serialized, Then the existing `redact-sensitive-data` skill runs as a pre-write gate; violations block the write.
- [ ] AC-5: Given the episode store exceeds a configurable size cap, When a new episode is written, Then the lowest-value episodes (low outcome score + old + never replayed) are garbage-collected with a summary commit.

**Priority:** Must Have

### US-2: Similarity-based replay on new tasks

**As a** Senior Dev,
**I want** `/autorun` to surface past similar episodes at Phase 1 (Intake),
**So that** the agent starts warm with relevant precedent.

**Acceptance Criteria:**
- [ ] AC-1: Given a new PBI intent, When Phase 1 starts, Then skill `trace-replay` computes an embedding of `(intent || detected_modules || detected_contracts)` and retrieves top-k episodes (k configurable, default 3).
- [ ] AC-2: Given top-k episodes are retrieved, When they are injected into context, Then they appear as a dedicated `EPISODIC_MEMORY` block with explicit provenance (episode id, date, outcome score), **not** blended into the system prompt.
- [ ] AC-3: Given an episode has `outcome: failed`, When it is in top-k, Then it is labelled `NEGATIVE_EXAMPLE` and accompanied by the failure reason.
- [ ] AC-4: Given replay is available, When the harness runs, Then a trace event `{type: "episode_replay", episode_ids: [...], similarity_scores: [...]}` is emitted for later auditing.
- [ ] AC-5: Given the user runs with `--no-replay`, When `/autorun` starts, Then no episodes are retrieved and the run is flagged in the trace (supports A/B comparison).
- [ ] AC-6: Given retrieval returns zero episodes above the similarity threshold, When the run continues, Then it proceeds cold-start with a trace note, not a stall.

**Priority:** Must Have

### US-3: Outcome scoring

**As a** Toolkit Maintainer,
**I want** each episode to carry a numeric outcome score derived from objective evidence,
**So that** replay prefers high-quality precedents and decays bad ones.

**Acceptance Criteria:**
- [ ] AC-1: Given an episode completes, When `outcome_score` is computed, Then it combines: tests-green (0.4), review verdict (0.3), contract-compliance (0.2), review round-trips (0.1) — all derivable from the existing spec-008 evidence bundle.
- [ ] AC-2: Given a post-merge regression is later detected (via `drift-detector` or manual tag), When an episode-level correction is recorded, Then the episode's `outcome_score` is decremented and a `regression_event` is appended.
- [ ] AC-3: Given a score falls below a threshold (configurable, default 0.3), When replay runs, Then that episode is excluded from positive examples but may still appear as `NEGATIVE_EXAMPLE`.
- [ ] AC-4: Given a user manually tags an episode (`/autorun episode tag <id> --bad "hallucinated endpoint"`), When replay runs, Then the manual tag overrides computed score.

**Priority:** Should Have

### US-4: A/B measurement surface

**As a** Toolkit Maintainer,
**I want** to measure whether replay actually improves outcomes,
**So that** the feature is kept honest and not kept on faith.

**Acceptance Criteria:**
- [ ] AC-1: Given N recent runs exist, When I run skill `review-effectiveness --episodes`, Then a markdown report compares `replay-on` vs `replay-off` runs across: token cost, first-attempt test pass rate, review round-trips, time-to-PR.
- [ ] AC-2: Given the difference is statistically thin (< 5% on all metrics over ≥ 30 samples), When the report renders, Then it recommends disabling replay by default for the current repo.
- [ ] AC-3: Given the report runs, When replay is enabled, Then at least 20% of recent runs must have been `--no-replay` for the comparison to be valid; otherwise report flags insufficient control data.

**Priority:** Should Have

### US-5: Negative examples ("don't do this")

**As a** Senior Dev,
**I want** failed episodes to be surfaced explicitly,
**So that** the agent doesn't re-attempt known-bad approaches.

**Acceptance Criteria:**
- [ ] AC-1: Given a top-k retrieval, When ≥ 1 negative episode is above similarity threshold, Then it appears in the `EPISODIC_MEMORY` block clearly prefixed `NEGATIVE_EXAMPLE` with the failure mode summarised in ≤ 2 sentences.
- [ ] AC-2: Given a negative episode is surfaced, When the agent drafts its plan, Then the plan must include a `risks` entry referencing the episode id; the `review-spec` skill validates this reference.
- [ ] AC-3: Given no negative episode is relevant, When retrieval returns positives only, Then no placeholder text is injected (avoid context bloat).

**Priority:** Should Have

### US-6: Privacy & export control — **DEFERRED (post-v1)** (D-3)

> Cross-repo episode pack sharing is out of scope for v1. Only AC-3 (local PII redaction on write) survives and is re-homed under US-1/AC-4.

**As a** Platform Engineer,
**I want** episodes to be exportable and redactable before cross-repo sharing,
**So that** private repo data doesn't leak when skill packs are shared.

**Status:** Deferred to a follow-up spec. A signed-export mechanism will be re-evaluated after v1 A/B data exists.

**Priority:** Won't Have (v1)

## 9. Assumptions

- A1: Spec 008 (`/autorun` + JSONL trace) is merged before this feature starts implementation.
- A2: Local embedding model (≤ 100 MB) is acceptable for the target repos; remote is opt-in via config (not default).
- A3: Episode store lives inside `.github/.episodes/` and is committed by default; repos that want ephemeral memory can `.gitignore` it.
- A4: Repos using this feature have the `correction-ledger` skill already (it's part of the default bundle).
- A5: A 20-run cold-start window on this repo is a sufficient baseline; benchmarking against external corpora is out of scope for v1 (D-7).

## 10. Resolved Decisions (was: Open Questions)

| ID | Decision | Chosen option | Rationale |
|---|---|---|---|
| D-1 | Embedding backend default | **ship-local-onnx** — bundle ONNX MiniLM-class model (~80 MB) | Offline, deterministic, no outbound call; aligns with NFR-3 and NFR-5. |
| D-2 | Episode retention policy | **score-gated** — keep while `outcome_score ≥ threshold` and not superseded | Prevents stale-precedent accumulation; quality-over-quantity. |
| D-3 | Cross-repo sharing boundary | **no-cross-repo-v1** — US-6 deferred | Removes signing/trust-model complexity from v1; revisit with real A/B data. |
| D-4 | Similarity threshold default | **0.75** (original guess, calibrate later via `review-effectiveness`) | Ship with a concrete value; FR-11 schedules calibration after 30 episodes. |
| D-5 | Negative-example cap | **max 2 per run** | Tighter than positive k (default 3); keeps EPISODIC_MEMORY block bounded. |
| D-6 | Correction-ledger integration | **orthogonal-streams** — ledger stays flat; episodes are separate in v1 | Minimises coupling; re-evaluate once both streams have usage data. |
| D-7 | Baseline source for §2 metrics | **measure-from-spec-008-runs** — 20 runs with `--no-replay` form the baseline | Avoids guessing targets; FR-11 enforces the measurement gate before claiming improvement. |

## 11. Risks

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Context bloat from injected episodes | Medium | Reduces benefit, may harm runs | Hard byte cap on `EPISODIC_MEMORY` block; compress episodes to structured skeleton |
| Poisoned episodes (hallucinations persisted as precedent) | Medium | Compounding errors | Pre-write validation hook; outcome-score threshold; regression-event decay |
| Prompt injection via replayed user text | Medium | Harness takeover | Store `raw_intent` separately; never merge into system messages; sanitize-untrusted-input skill |
| Privacy leak via exported pack | Low | High | Mandatory `redact-sensitive-data` gate on export; explicit allow-list on import |
| A/B measurement bias (users disable replay only when struggling) | High | Metrics misleading | Force random 10% cold-start runs for control |
| Embedding drift across model versions | Medium | Retrieval quality decays | Record embedding model id; rebuild index on upgrade |
